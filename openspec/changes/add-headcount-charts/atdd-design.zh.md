> 场景标题、`S1`–`S12` 等规范标识保留英文原文，便于与规格和 tasks 的追溯表逐项对照。

- **变更 ID：** `add-headcount-charts`
- **门禁背景：** G1 于 rev 2 通过（2026-11-11，`g1-decision.md`）；本文是 `/sdd:task-plan` 的 P3 输入
- **被测规格：** `specs/staffing/headcount-report/spec.md` —— 6 个需求 / 12 个场景
- **适用的规则：** `testing-strategy`、`pipeline-gates`、`architecture-baseline`
- **视觉基准：** `prototype/` —— G1 评审接受的三状态原型。§6 把它的每个元素映射到将要构建的东西，并点名两部分仅用于评审。
- **本文范围：** 验收层次（API + E2E）、先于产品代码写下的检查、门禁对齐与夹具。不设计单元测试套件，不写功能代码。

## 1. 范围内的 ATDD 层次

| 层次 | 证明什么 | 形态 |
|---|---|---|
| **API** | 成员口径、顺序、占比、空池答案、拒绝 | 对真实 H2 schema 发一次 HTTP 请求，无界面 |
| **E2E** | 只有渲染后的页面能证明的：区块存在、柱高成比例且有文字标注、LEAD 看不到区块、空态文案 | 浏览器 + 种子账号，4 个场景 + 1 条旅程 |
| **延后 UT** | 下列纯逻辑 | 由 `/sdd:atdd-apply` 在实现期做红绿 |

| 需求 | 需求数 | 场景数 | API 主层 | E2E 主层 | 延后到 apply（单元 TDD） |
|---|---|---|---|---|---|
| R1 只描述启用池 | 1 | 2 | 2 | 0 | 仅启用判据；总数 = 两轴之和的不变量 |
| R2 轴与其顺序 | 1 | 4 | 4 | 0 | 轴 = 启用角色 ∪ 仍持有在职人员的角色；带序来自 `Bands` |
| R3 人数与占比 | 1 | 2 | 2 | 0 | 一位小数四舍五入；`100.0` 与残差情形 |
| R4 人员池页面上的区块 | 1 | 2 | 0 | 2 | 柱高由最高柱推导；0 值柱的刻度 |
| R5 仅协调员 | 1 | 1 | 0 | 1 | ——（复用门禁） |
| R6 空池被陈述 | 1 | 1 | 0 | 1 | 空答案的形状 |
| **合计** | **6** | **12** | **8** | **4** | —— |

每个场景恰有一个主层，所以没有场景被丢弃，也没有场景被重复计数。4 个 E2E 场景中有两个带一层便宜的 **API 伴随** —— S9 的直连 403 与 S10 的零总数答案 —— 它们不增加场景行。

### 4 个 E2E 场景

| 场景 | 为什么不能只在 API |
|---|---|
| S8 Both charts sit on the pool screen | 「没有别的屏幕可达」是关于应用导航的陈述，不是关于载荷的 |
| S9 A lead sees no report | 主张是区块的**缺席**加请求的**缺席**；只有浏览器能同时证明 |
| S10 An empty pool says so | 主张是替换掉两张图的那句渲染文案 |
| S12 The table and the charts differ on purpose | 两个数字必须在同一屏上同时读到 |

旅程 **J1** 把它们串起来而不增加场景：导入一个把某人移入 `PM`、并把另一人停用的工作簿 → 打开 `/people` → 两张图变化而表格保留停用行。J1 同时充当 §7 的新鲜度检查。

### 延后到 `/sdd:atdd-apply`（单元级 TDD）

恰好落在半值上的四舍五入（`1/8` → `12.5`）· 轴判据（启用角色无人仍在轴上；停用角色无人不在轴上）· 带序与角色序来自存储顺序而非人数 · 最高柱为 0 时的柱高（由空态兜住）· 零人数的占比为 `0.0` 且绝不做除法。这些是实现期红绿的入口，不是套件计划。

## 2. 先于产品代码写下什么

1. **夹具**（§4）：账号与通过导入路由构造的人员池。
2. **报表路由的 API 检查**，按此顺序 —— 成员口径与总数不变量 → 顺序 → 占比 → 空答案 → 403。它们在 `HeadcountController` 存在之前是红的。
3. **E2E 检查**：S8、S9、S10、S12 与 J1，在区块存在之后写。
4. **单元测试**：实现期随代码写，绝不在此设计。

每项检查都点名其场景标题；没有场景的检查说明规格集有问题，而不是测试有问题。

## 3. 本地与 CI 门禁

对齐 `pipeline-gates`；不引入第二套 CI 语义，不新增作业。五项检查的工作流已存在（`.github/workflows/ci.yml`），本变更只往里加测试：

| 检查 | 位置 | 说明 |
|---|---|---|
| lint、类型检查 | 本地 + CI | 新的 `web/tests/headcount.test.ts` 必须加入 `package.json` 显式的 `npm test` 清单，且 `tsc --noEmit` 要能看到它 |
| 单元测试 | 本地 + CI | 随代码写；JaCoCo 对 `domain*` / `api*` 保持行与分支 100% |
| 验收 —— API | 本地 + CI | 8 个 API 场景 |
| 验收 —— E2E | 本地 + CI | 4 个场景与 J1 |
| 依赖与安全扫描 | CI | 不变；本变更不新增依赖 |

停止检查顺序：静态 → 单元 → API 验收 → E2E；某层红则停住下一层。

## 4. 数据与夹具

- **账号（固定）：** 种子里的 `coordinator`、`lead.one`、`lead.two`；第二个项目经理用来证明 403 与归属无关。
- **轴需要一个无人的角色。** 种子目录提供 `PM, BA, DEV, QA, UX`；需要 0 值柱的测试就往某个角色里不导入任何人，并断言该角色仍在轴上。
- **人员池一律通过导入路由构造**，绝不用直接 SQL，这样夹具无法造出服务端会拒绝的东西。值得在夹具里钉死的数字形状：角色顺序用 113 = 40 + 25 + 14 + 34 + 0；四舍五入用 3 人 / 8 人的池（`1/3` → `33.3`、`2/3` → `66.7`、`1/8` → `12.5`）。
- **工号**取每个测试自己的命名空间（`H1xx`），两个测试类不会撞号；每个测试类一个全新 schema（既有的 `${random.uuid}` 数据源 URL），报表不会读到别的测试的行。
- **本变更没有日期、没有时钟、没有随机**：每条断言都是一个人数、一个顺序、一个占比或一个状态码。

## 6. 与原型对齐

原型是已同意的画面；下表是让实现保持诚实的对账表。

| 原型元素 | 构建成什么 | 说明 |
|---|---|---|
| 黄色「评审状态」切换条 | **不构建** | 仅评审用的装置；产品里每个登录角色只有一种状态 |
| 区块位于人员池两栏之上 | `HeadcountSection` 插在 `PeopleScreen` 的 `.grid-2` 之上 | 顺序有意义：先区块，再表格 + 档案 |
| 两张卡片 `Headcount by Role` / `Headcount by Grade` 与 `Total <n>` | `ChartCard`：标题 + 总数行 | 总数是**启用**池，标签要说清 |
| 纵轴刻度由最高柱推导 | `lib/headcount.ts` 的 `ticks(top)` | 取整步长（10 或 2），顶部向上取整 |
| 柱高与人数成比例、数值印在柱上方 | `.bar` 的行内高度 + 兄弟元素里的数值 | 高度来自服务端的 count，绝不客户端重算 |
| 0 值柱画成细灰刻度，标签 `0` / `0.0%` | `.bar.is-zero`（3px）+ 变淡的标签 | 0px 元素不可见；这个刻度就是「该分类存在」的证据 |
| 标签按目录 / 带序 | 按服务端顺序渲染 | 客户端从不排序 |
| 虚线空块写着「无启用人员」 | 两张卡片内的 `chart-empty` | 按要求替换掉绘图区 |
| 「图上元素与规格条款」对照卡 | **不构建** | 仅评审辅助 |
| LEAD 态：无区块、403 说明 | 区块不渲染，且**不请求**报表 | 先读角色 —— 见 §7 |

两条**不得**泄漏进产品的原型行为：状态切换条、对照卡。两条**必须**保留：0 值柱刻度、「先知道角色再取数」的顺序。

## 7. NFR 测试（范围内：授权 + 新鲜度）

已在本次会话中与产品负责人确认。

**授权（API + E2E）。** 报表答给协调员、对项目经理返回 403 且不改变任何状态；人员池页面对项目经理不渲染图表区块，也不发出报表请求。后半句正是设计要先读 `GET /api/session` 的原因：先渲染再按 403 隐藏，请求已经发出去了，S9 照样失败。这与 `CatalogScreen`、`PostScreen` 现有取角色的做法一致。

**新鲜度（API）。** 报表每次读取即时派生，不持有缓存。一个测试先读一次，再应用一次把某人移入别的角色的导入，再读一次：人数、占比与轴在第二次读取时改变，且不存在任何报表行可供过期。同一测试还断言停用人员离开图表而表格仍在展示。

**延后，附理由：** 性能（人员池数千行、报表一次分组读取 —— 没有使用画像的时延预算只是编出来的数字）；可观测性（没有批次要审计、没有定时作业；报表能记的东西请求日志已经有了）；韧性、兼容性、可访问性与协议（单一浏览器目标、无外部服务、无流式）。可访问性被点名是因为柱是视觉的：每根柱都以文字带出人数，信息从不只是一块矩形 —— 这是规格层的属性（R3），不是 ARIA 审计。
