# 提案：按角色与按等级的 Headcount 图表

- **变更 ID：** `add-headcount-charts`
- **状态：** 已提议 — P1 完成；下一步 `/sdd:delta-craft`（P2）与 G1 签署
- **需求：** `requirement-workspace/requirements/REQ-002-headcount-charts.md`（rev 1，S1–S12）
- **影响简报：** `requirement-workspace/analysis/impact-brief-REQ-002-headcount-charts.md`
- **意图来源：** `requirement-workspace/intents/INT-002-headcount-charts.md`
- **规模：** S（一个能力、一个只读路由、人员池页面内的一个图表区块）
- **评审辅助：** `prototype/` —— 图表区块的静态可点击原型，含三个状态（协调员·有数据、协调员·空池、项目经理）；无构建、无依赖，用任意静态服务打开 `index.html` 即可。
- **脚手架说明：** 本机未安装 `openspec` CLI，因此本变更包按仓库既有布局直接书写，未走 `openspec new change`；文件集与标题与 `add-staffing-mvp` 保持一致。

## 为什么

人员池已经保存了每个人的角色、职级与启用标记，但没有任何界面展示池子的形态。协调员要判断某个角色是否稀缺、公司是否头重脚轻时，只能通过 `/people` 逐人查看。

这带来两项具体成本：

1. **数据已经能回答的问题没人问。**「我们有几个 `QA`，占全池多少？」需要在按工号排序的表格里手工数一遍。
2. **答案不可共享。** 两个协调员手工统计时会对「是否算进了离职人员」产生分歧，而且谁也指不出一个被一次性定义过的数字。

两张柱状图——按角色的人数和按等级的人数——把手工统计变成一次读取：每根柱子带人数与占比，每张图带总数。

## 变更内容

1. 新增一个**只读聚合端点**，一次返回快照：启用人数、角色轴上的每个分类一根柱、每个职级带一根柱。只读 `person`、`role.name` 与 `role.active`，不写任何数据；无新表、无 schema 变更。
2. **统计口径与轴在服务端一次固定。** 只统计 `active = true` 的人员；轴上的每个分类都保留自己的柱（即使为 0），因此最后一名人员离开时柱子不会消失；总数即启用人数，因此必然等于任一轴的柱子之和——两条轴描述的是同一个池子。
3. **每根柱子带两个数字。** 原始人数，以及占总数的百分比（一位小数、四舍五入）：113 人中的 40 人读作 `35.4`。四舍五入后占比合计可能是 99.9 或 100.1，人数永不为了凑成 100.0 而调整。
4. **顺序来自模型，不来自大小。** 角色柱按目录顺序（角色 id），等级柱按带序（`Junior` < `Senior` < `Lead` < `Principal`），因此只有在数据变化时图形才变。
5. 两张图成为**人员池页面（`/people`）的一个区块**，画在人员表上方：每根按比例绘制的柱、柱上的人数与占比、图上方两个总数，以及池中无启用人员时的空态。不新增路由、不新增屏幕：池子的形态和它统计的人在同一页读完。该区块只对协调员渲染——壳层 `nav.ts` 里的「人员池」入口本来就属于该角色，因此导航无需改动。

### 本提案固定的关键规则

- **一个池，两条轴。** 两张图描述同一批启用人员，因此两个总数按构造相等，且各自等于本轴柱子之和。作业简报中两张插图的示例数字不同（113 与 108），是因为它们是两张独立的示例图；在系统里两个总数出现差异即为缺陷。
- **只算启用。** 离职/停用人员既不进柱子也不进总数，与匹配门禁 G1 读取的同一个标记保持一致。
- **空分类保留自己的位置。** 轴是目录仍提供的每个角色（`active`）、所有仍持有启用人员的角色，以及四个职级带。没有人的分类保留一根 0 高的柱，读作 `0` / `0.0%`，因此只要角色仍被提供，它就不会从图上消失。唯一离开轴的是已停用且无人的角色，因为目录已不再提供它；当池中完全没有启用人员时，空态会替换两张图，因为最高柱为 0 的图没有可绘制的刻度。
- **占比只舍入一次，且不做修正。** 一位小数、四舍五入。人数保持精确，合计为 99.9 或 100.1 的残差被接受，不重新分配。
- **顺序来自模型。** 角色按目录顺序，等级按带序；两轴都不按人数排序，因此同一个池子永远产生同一版布局，图形从不暗示排名。
- **停用的角色仍统计其在职人员。** 柱子使用库中存储的 `role.name`；在目录里停用一个角色不改变任何数字，正如停用角色在候选人搜索中仍然照旧参与门禁。
- **报表属于协调员，LEAD 看不到任何痕迹。** 它是协调员本就能读取的人员池的聚合，因此端点对 LEAD 返回 403，人员池页面也只对协调员绘制图表区——没有占位、没有拒绝文案、没有数字。壳层早已如此：`lib/nav.ts` 的「人员池」只给 `COORDINATOR`，`smoke.spec.ts` 也断言 LEAD 看不到该链接。报表不放宽该可见范围，也不携带任何个人明细——柱子是计数，永远不是姓名清单。
- **同一屏上两个数字，两种含义。** 人员表列出所有导入的人员（含已停用），图表只统计其中在职的。这是有意为之，图表区的总数行会说明它统计的是哪个池。
- **不存储任何东西。** 每次读取即时派生；没有报表表、没有快照、没有定时任务。人员池一变化，下次读取即可见。

### 变更内部的交付顺序

领域聚合与舍入 → 只读路由及其 403 → `PeopleScreen` 内的图表区块与它的协调员门禁 → 测试与验证报告。每一步都可以在上一步之上演示。

## 非目标

- **不做筛选、下钻或时间序列。** 图表始终描述当前整个启用池；筛选会改变统计口径，属于独立需求。
- **报表上没有任何写路径。** 屏幕上的任何操作都不改变人员、角色或职级。
- **不新增表、列或迁移。** 数据已经存在。
- **不含个人明细。** 工号、姓名、邮箱、技能、分配都不进入答案。
- **不做导出、图片下载或定时推送。**
- **不做按项目、按负责人或按角色的再细分。**
- **不强制引入图表库。** 需求只固定比例与标注；实现机制由设计决定，在本仓库中纯标记是更省的选择。

## 影响

### 自身（本变更）

- `staffing/` 下一份能力增量规格，及其中文译本、设计与任务。
- 后端：一个只读聚合服务及其视图记录、一次仓储读取、一个只有单个 `GET` 的控制器，以及它们的测试。既有的 `domain*`、`api*` 行与分支 100% 覆盖率门禁适用，因此测试随代码一起交付。
- 前端：`PeopleScreen` 内一个带协调员门禁的图表区块、一个承载该区块纯函数读法的 `lib` 模块，以及一个加入 `package.json` 测试清单的测试文件。不新增路由、不新增屏幕，`App.tsx`、`AppShell.tsx`、`nav.ts` 均不改动。
- registry 与 handoff 各增加一行 REQ-002。

### 上游

- 读取 `add-staffing-mvp` 已经写好的 `person`（`role_id`、`job_level`、`active`）与 `role.name`。不修改该变更的任何路由或契约。
- 复用 `api/Auth.coordinator`，与 `/api/people` 同一把锁。

### 下游

- 不影响任何既有消费方：没有路由改变形状，LEAD 的首页视图仅少一个入口。
- 后续可能因此开展的工作（各自独立变更）：池子 KPI 磁贴、项目或日期筛选、利用率报表。本变更都不隐含。

## 假设

1. Headcount 指人数，不是岗位 headcount 之和。
2. 人员池规模在数百到数千行量级，每次请求做一次分组读取即可；不做缓存，不做物化视图。
3. 「占总数的占比」中的总数指启用池总数，也是两张图唯一展示的总数。
4. 角色轴只在一个方向上由数据驱动：一个角色一旦成为目录中的启用项就出现，并一直以 0 值留在图上，直到目录把它移除；代码不硬编码五个种子角色。等级轴永远是四个带。
5. 职级沿用 REQ-001 的四带刻度；报表从不展示数字序号。
6. 运行时沿用 ADR-001 记录的技术栈——React 19 + TypeScript SPA 与 Spring Boot on H2；本变更不新增依赖。

## 工作量与风险

- **规模：** S。一个能力、一个路由、一个屏幕，无 schema 变更；是本仓库能够端到端走完的最小变更。
- **主要风险：** 简報中两个总数不同，读者可能认为两张图覆盖两个人群。缓解方式是把「一个池」写成规则并落到场景 S1，同时在 D2 记录另一种可能。
- **第二风险：** 舍入后合计不到 100.0 会被当成缺陷。缓解方式是唯一一条舍入规则（一位小数、四舍五入），并明确接受残差。
- **第三风险：** 半张图都是 0 值柱会让人以为没数据。缓解方式是总数行说明它统计的是哪个池，且一旦无人启用就由空态整块替换两张图——因此 0 值柱只会与至少一根真实柱子同时出现。
- **第四风险：** 新类若不测试，覆盖率门禁会让构建失败。这是约束而非风险：测试属于本变更。
