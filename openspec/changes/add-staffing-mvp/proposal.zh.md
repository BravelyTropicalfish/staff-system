## 为什么做

公司同时在跑多个项目，会反复遇到需要“为新项目填补岗位”或“填补已有项目的空缺岗位”的情况。目前这些决定靠人工完成：项目经理描述岗位需要什么，资源协调员凭记忆在人员池里翻找。结果好坏取决于谁记得哪个员工的角色、职级和技能合适，谁记得此人在这段时间是否有空，以及是否接受该项目要求的出差。

这种工作方式造成三类具体损失：

1. **重复占用（双重派工）。** 系统没有记录“某人已被确认占用”，同一个员工可能被算进两个项目。
2. **找人慢、判断不一致。** 角色、职级、技能熟练度、占用与差旅意愿，每个协调员的权衡方式都不同，而判断理由在讨论结束后就丢失了。
3. **没有共享的缺口视图。** 项目经理和协调员对“哪些岗位还缺人”认知不一致，因为已确认的人员和剩余名额分散在不同人的脑子里或各自的表格里。

本 MVP 让两个角色在同一份数据上走同一条流程：项目经理提岗位，协调员从通过门槛的人里挑选并推荐人员，项目经理确认，双方都能看到谁已到位、还缺什么。

人员主数据本来就以报表形式从 HR 流出，因此系统必须把这份报表当作批量数据入口，而不是让协调员把每个员工、每个职级和每项技能重新敲一遍。

## 变更内容

在现有空基线上从零构建一个新的 Staffing 应用，具备以下端到端行为：

1. **资源协调员**维护角色目录与技能目录，人员与岗位共用这两个目录。目录项一旦被任何数据引用，就不能再改名或删除，只能停用，使已有人员与岗位继续按同一目录项匹配。
2. 人员主数据通过**报表**进入系统：协调员上传一个 `.xlsx` 工作簿，包含 `people` 与 `skills` 两张表，以工号为键。整份文件是一个工作单元 —— 所有行都必须通过校验，否则系统一个字都不写，所有出错的行一次性列进本批次错误清单，由协调员修正后重传。无法作为工作簿读取的文件 —— 缺一张表，或两张表都没有数据行 —— 在上传时即被拒绝，且不记录任何批次，使“拒绝上传”与“批次被驳回”区分开。`people` 表中工号在系统里不存在则新建人员；技能不在目录、工号重复、必填单元格为空、`skills` 行孤儿、取值不在受控集合内，任意一条都会让整份批次失败。报表中未出现的技能保留原有等级。每个单元格都必须落在受控取值集内：五类角色、四档职级、预置技能与五档熟练度。
3. 协调员同时维护**项目**（含项目经理）与**占用记录**（allocation）：某人被某项目占用的一个闭区间日期范围。确认时按岗位起止日期写入占用，协调员也可手工录入；两条手工录入的区间可以重叠，重叠作为事实保存而不被拒绝。项目经理结束时项目变为 `closed`，其岗位全部取消，该项目下的所有占用在同一动作里释放。
4. **项目经理**为项目提出岗位需求：角色、最低职级档、技能（分 `required` 必备与 `bonus` 加分，分别带最低/目标熟练度档）、招聘名额、项目起止日期、差旅要求。
5. 系统针对一个岗位，先**排除**未通过硬性门槛的人（停用、角色不符、职级不足、缺少某项必备技能或熟练度不够、不接受该项目差旅、已有日期区间与岗位相交的占用），再把**通过全部门槛的人全部列出**：按姓名升序，不打分、没有排序偏好 —— 清单只说“这些人合适”，从不说“这个人最合适”。每一行展示该员工的角色、职级、差旅意愿、通过的门槛，以及使其合格的那些技能及其档位：`required` 行给出已达到的档位，`bonus` 行给出已达到的档位与目标档。`bonus` 不足只作信息展示，既不排除任何人，也不改变任何人的位置。由协调员决定推荐谁；系统永远不会指出“最佳人选”。被门槛排除的人单独列出并给出首个未通过的门槛，再附上每个门槛的排除计数，让空清单有解释而不是静默。当该岗位的角色一个人都筛不出来时，系统另外给出一份**跨角色兜底**名单，列在其他角色的员工下方：职级至少比岗位要求高一级，且岗位角色技能域内有一项技能达到 `Practitioner` 及以上。
6. 协调员**推荐**清单上的某位候选人。推荐记录携带推荐当下那一刻的理由快照 —— 通过的门槛与使其合格的技能。
7. 项目经理**确认或驳回**。确认前系统重跑在职与占用两条门槛；通过后写入指派与一条覆盖岗位起止日期的占用、剩余名额减一、占满最后一个名额时岗位变为 `filled`，并把该员工在其他岗位、日期与新占用相交的未决推荐自动作废。驳回则释放该人员。岗位有人被确认后，其参与门槛校验的字段（角色、最低职级、`required` 技能、起止日期、差旅）全部锁死，名额只能上调；岗位名称与 `bonus` 技能仍可修改。取消岗位必须先解除已确认人员。
8. 双方获得**共享的缺口视图**：按岗位显示已选定人员、已到位数量与剩余名额。
9. 项目经理在项目完成时**结束项目**：项目永久变为 `closed`，其岗位全部取消，未决推荐作废，派在项目上的所有人一次性释放，于是会重新出现在其他项目的搜索里。

| `staffing/people-pool` | 角色与技能目录（每项技能声明归属的角色技能域）、员工档案、按报表写入的技能熟练度与差旅意愿 | M |
| `staffing/people-import` | 上传人员主数据工作簿：整份文件校验、全有或全无写入、增量合并、按批次错误清单、批次历史 | M |

| `staffing/post-requirement` | 岗位：角色、职级、必备/加分技能、名额、日期、差旅；编辑与取消规则；open / partially filled / filled / cancelled | M |

### 本提案确定的规则

- 角色是预置五值的目录 —— `PM`、`BA`、`DEV`、`QA`、`UX`；技能是另一个独立目录，预置后端开发、前端开发、项目管理、业务分析、测试、UI设计。两者由人与岗位共用，且仍可扩展。
- **一人一角色。** 每个人员恰好只有一个角色，以单一目录引用保存，永远不是集合。技能是另一个目录，因此持有“测试”技能不会让一个 `DEV` 同时成为 `QA`；报表里写两个角色的单元格会被驳回，而不是被拆成两个角色。岗位因此只会看到本角色范围内的候选人（合适清单内）。
- **跨角色兜底是更低的层级，不是放宽门槛。** 只有当该岗位角色一个人都筛不出来时，才会额外展示其他角色的员工：职级至少比岗位要求高一级，且在岗位角色的技能域内至少持有一项 `Practitioner` 及以上的技能。他们单独一栏，与主清单一样按姓名排序，永不混入其中。岗位角色不会被写到人身上：兜底只是一次临时的配置建议，不是第二个角色。
- **每项技能只归属一个角色技能域。** 后端开发与前端开发构成 `DEV` 域，测试归 `QA`，业务分析归 `BA`，项目管理归 `PM`，UI设计归 `UX`；后续新增的角色初始为空。技能域只服务于兜底，绝不放宽 G4（G4 仍是逐岗位、逐技能校验）。
- **三套有序档位。** 职级为 `Junior` < `Senior` < `Lead` < `Principal` 四档；技能熟练度为 `Novice` < `Advanced beginner` < `Practitioner` < `Proficient` < `Expert` 五档；差旅意愿为 `none` < `limited` < `full` 三档。所有比较都按档位次序进行，UI 只显示档位名称，不显示数字。
- **人员主数据来自报表，不来自表单。** 以工号为键，工号为空或重复即报错。报表里出现的字段覆盖系统已有值；报表未出现的技能保留原熟练度；任何数据都不会因报表缺失而被删除。
- **导入是全有或全无。** 只要有一行不合法，整份批次失败，人员池保持原状；错误清单把所有出问题的行一次列全，改一轮、重传一次即可。
- 人员主数据在系统内没有编辑入口。写错的值通过重新上传修正后的报表来纠正，因此每次变更都留下不可篡改的批次记录。
- **职级是员工属性，也是岗位的最低要求。** 技能熟练度是“人 × 技能”上独立的档位，岗位的每项技能也各自有最低/目标熟练度档。
- **岗位技能分两类。** `required` 是硬门槛；`bonus` 仅作信息展示，给出已达到的档位与目标档。加分技能不达标的候选人仍然通过，不足也不会改变任何人的位置。缺少必备技能才会被排除。
- **同一人可被推荐到多个岗位。** 以先确认者为准，该员工日期与新占用相交的其余未决推荐自动作废（原因“人员已被占用”），并在协调员的提示列表中列出；日期不相交的推荐保持 `proposed`。
- 差旅在人与岗位两侧都是有序三档 —— `none` < `limited` < `full` —— 不带任何日期：员工意愿档位 ≥ 岗位要求档位即视为接受，差旅不建模其他维度。
- **占用占住它的日期。** 占用带闭区间的起止日期 —— 确认时取岗位日期，或由协调员手工录入。G6 挡住任何日期与它相交的岗位（两端闭合），因此一条在岗位开始日结束的占用同样会挡住它；更晚且不重叠的岗位则不受影响。项目结束仍会释放该项目下的所有占用。
- 只有岗位所属项目的项目经理可以确认；只有资源协调员可以推荐。
- 确认后的人员会写回为一条覆盖岗位日期的占用，因此该员工在日期相交的其他岗位上自动排除。
- **岗位生命周期。** 岗位存在已确认人员时，角色、最低职级、`required` 技能行、起止日期与差旅全部锁死，名额只能上调（上调超过已确认人数时岗位回到 `partially filled`）；岗位名称与 `bonus` 行仍可修改，但会作废未决推荐。取消岗位前必须先解除已确认人员；解除（负责人或协调员均可）会删除指派与占用并重新开放名额。**结束项目**是项目经理的终态动作：岗位全部取消、未决推荐作废、该项目所有占用一步删除 —— 这是唯一能在不逐个解除的情况下清空岗位的路径；已结束项目不可重开。
- **目录项只停用、不删除。** 角色或技能一旦被人或岗位引用，名称就冻结；可停用使其不再出现在新建岗位与导入选择中，但所有已存引用继续有效。
- **项目经理只能看到被推荐给他的人**及其理由快照 —— 通过的门槛与使其合格的技能；完整候选池、合适清单与排除原因只对协调员开放。
- **不打分、不排序。** 通过门槛本身就是全部判断依据：所有合适的人按姓名列出，系统不计算契合度得分、不按偏好排序、也不指出最佳人选。日后若要引入评分，属于规格变更。

### 单个变更内部的交付顺序

流程是线性的，因此任务按流程排列：目录 → 报表导入 → 项目与占用 → 岗位与缺口视图 → 匹配 → 推荐与确认。每个阶段都能在前一阶段基础上独立演示。

## 非目标

- **不做外部集成。** MVP 不接 HR、项目管理或日历系统，也不做定时或推送式文件落地：协调员手工上传工作簿。
- **不做手工编辑人员主数据。** 人员、角色、职级、技能与差旅意愿只能通过导入批次变化。
- **不做部分投入。** 一条占用在其闭区间内完整占住该人员；投入百分比延后处理。
- **不做自动指派。** 系统永不自行确认人选，由人来决定。
- **不做通知。** 无邮件、无 IM；状态变化只在应用内可见。
- **不做成本、费率、预算和利用率报表。**
- **不做面试或多级审批链**，只有项目经理的确认/驳回。
- **不做移动端、离线模式、多公司租户。**
- **不做按目的地细分的差旅**，差旅仍是三档意愿。
- **本变更不包含生产部署流水线**；只做本地运行与测试。

## 影响面

### 自身（本变更）

- 创建整个应用结构：UI、业务逻辑（门槛、合适清单、写回）与数据访问，按 `architecture-baseline.md` 分层隔离。
- 创建 `staffing/` 下六个能力的 delta spec，以及 design 与 tasks。
- 创建首批测试：门槛、合适清单的姓名顺序、跨角色兜底、导入校验、岗位生命周期、目录停用、项目结束与写回的单元测试；覆盖 REQ-001 场景 S1–S40 的 E2E 测试。
- 需要一份关于运行时技术栈的架构决策记录（见“假设”）。

### 上游

- 无。系统不消费任何既有服务、消息或数据集；人员通过导入进入，目录、项目与占用在应用内录入或由本地种子脚本载入。
- 仓库规则（`docs/knowledge/rules/**`）约束本次构建，但本身不发生变化。

### 下游

- 目前没有任何既有消费方依赖本系统，因此不会破坏其他东西。
- 未来可在此基础上开展的工作：HR 主数据同步（届时将取代手工上传文件）、投入百分比与利用率报表、通知、按目的地细分的差旅。每一项都是独立变更，本提案不隐含这些内容。
- `requirement-workspace/registry.md` 与 `handoff.md` 会新增本变更的登记行。

## 假设

1. 单一公司、内部用户；只有两个角色（项目经理、资源协调员）。登录为带角色的轻量账号，不接 SSO。
2. 一个岗位只属于一个项目，一个项目只有一个项目经理。项目经理只能看到自己的项目，协调员可见全部。
3. 名额为正整数；一个确认的人员完整占满一个名额。
4. 日期为同一公司时区下的日历日期，不处理一天内的时间。
5. 职级为四档、技能熟练度为五档。档位名称与顺序固定；只有岗位要求的阈值是数据。
6. 本提案不决定运行时技术栈。工作默认方案是 `shadcn/ui` 前端 + 小型强类型后端 + 关系型数据库；最终选择在实施前以 ADR 形式记录到 `docs/knowledge/architecture/` 下。
7. 报表是一个 `.xlsx` 工作簿，含 `people` 与 `skills` 两张表。真实 HR 导出的列名可能不同，统一在一个导入映射层处理（开放项 D4）。
8. 工号是人员唯一键，邮箱是普通属性。角色与技能目录在应用内维护，报表不能扩展目录。
9. 导入在 MVP 规模下同步执行（单文件数千行以内），因此不引入队列或后台任务。
10. 项目与其项目经理由协调员维护；项目经理不能自建项目，也不能把岗位挪到别的项目。
11. 技能的角色技能域是目录配置，不属于人员数据：报表不会携带它，修改它只影响此后的搜索。

| D6 | 删除人员身上错误的技能 | 产品 | MVP 无删除通道，只能通过停用技能项变通 |
| D7 | 岗位日期是否必须落在项目起止日期内 | 产品 | MVP 不做限制：岗位自带起止日期，超出项目区间的岗位不会被拦下 |
| D8 | 跨角色兜底是否需要名额上限（例如每岗位最多 3 人）或确认前的额外审批 | 产品 | MVP 不设上限：兜底栏与主清单一样按姓名排序，由协调员决定推荐谁；每次确认依然重跑在职与占用日期相交两条门槛 |

## 工作量与风险

- **规模：** L。六个能力、一条完整流程、一个全新应用；大致相当于一个中等规模特性团队一个迭代的投入。
- **主要风险：** 门槛阈值是政策选择而非客观事实 —— 岗位的最低职级、`required` 技能以及兜底的一档跨度，直接决定谁会出现。缓解手段是让这些选择成为岗位上的数据（兜底层级则写在能力规格里），每一行展示它通过了哪些门槛，每个被排除的人展示排除他的那个门槛，于是错误的阈值是可见的，而不是藏在多个因素的加权里。
- **次要风险：** 单个大变更意味着评审周期长。缓解手段是上文所述的线性任务顺序，让每个阶段都能独立演示。
- **第三类风险：** 全有或全无意味着一个错误单元格就会挡住整份上传。缓解手段是错误清单一次性列全，使一轮修正就能通过。
- **第四类风险：** 跨角色兜底看起来与“一人一角色”矛盾。缓解手段是规则的形状：G2 不动，兜底仅在同角色列表为空时开启，单独成栏且层级更低，且不会把第二个角色写到人身上 —— 它在推荐记录里记下“为什么提了这个角色的人”。
- **第五类风险：** 手工录入的两条占用可能重叠，人员表面上看已被占满，协调员却以为他有空；重叠也让两个区间都挡人。缓解手段是人员档案列出每条占用（当前或已结束）及其日期、G6 按闭区间比较，协调员可随时修正或删除手工录入的占用；确认写入的占用只随其指派一起消失。
