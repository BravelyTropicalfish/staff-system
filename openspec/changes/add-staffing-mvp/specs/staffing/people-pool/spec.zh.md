# staffing/people-pool —— 增量规格（中文译本）

> 本文是 `spec.md` 的中文译本，供评审阅读。两者如有冲突，以英文原版 `spec.md` 为准。
> 结构关键字（`ADDED Requirements` 段、Traces 行、GIVEN / WHEN / THEN / AND 标记）以及角色、技能、
> 档位、门槛与场景编号保留原样，便于与英文版逐项对照。

范围：角色与技能目录、人员主数据及其熟练度档位。人员数据只由 `staffing/people-import` 写入；本能力负责数据形态与读取界面。

## ADDED Requirements

### Requirement: 角色目录

系统应维护角色目录，条目携带稳定标识、名称与 `active` 标记，预置恰好五个角色：`PM`、`BA`、`DEV`、`QA`、`UX`。之后新建的角色，应能与预置角色一样被岗位、人员与导入使用。

**Traces:** proposal 步骤 1；REQ-001 §3、§5；S31。

#### Scenario: 首次使用时只有预置角色可选

- **GIVEN** 一个没有任何用户数据的库
- **WHEN** 协调员打开新岗位的角色选择器
- **THEN** 只提供恰好五条启用条目：`PM`、`BA`、`DEV`、`QA`、`UX`

#### Scenario: 新角色加入目录

- **GIVEN** 协调员新增角色 `SRE`
- **WHEN** 再次打开岗位表单
- **THEN** `SRE` 可选，且 `role` 单元格为 `SRE` 的导入行被接受

### Requirement: 技能目录

系统应维护技能目录，条目携带稳定标识、名称、该技能所属技能域的唯一角色，以及 `active` 标记；预置技能为 后端开发、前端开发、项目管理、业务分析、测试、UI设计。

**Traces:** proposal 步骤 1 与关键规则 "Every skill belongs to exactly one role domain"；REQ-001 §3、§5、§6 目录生命周期；S28。

#### Scenario: 技能选择器只提供预置技能

- **GIVEN** 预置目录且没有用户新增的技能
- **WHEN** 负责人打开岗位的技能选择器
- **THEN** 提供六项预置技能，不提供其他任何技能

### Requirement: 每项技能只归属一个角色技能域

系统应为每项技能存储恰好一个角色技能域 —— 即拥有该技能的那个角色 —— 且不得把同一技能放在两个角色下。预置映射应为 `DEV` → 后端开发、前端开发；`QA` → 测试；`BA` → 业务分析；`PM` → 项目管理；`UX` → UI设计。之后新建的角色应从空域开始，直到协调员为其分配技能。即使该技能已被引用，也应允许修改其域；改动应只对之后的候选人搜索生效，且不得改写任何已存的人员、岗位、推荐或快照。技能域只供给跨角色兜底使用：它不得放宽 G4，持有某项技能也从不使人获得第二个角色。

**Traces:** proposal 关键规则 "Every skill belongs to exactly one role domain" 与 "Cross-role fallback is a lower tier"；REQ-001 §5 词表（角色技能域）、§6 目录生命周期、§6.1。

#### Scenario: 预置映射按角色可读

- **GIVEN** 预置目录且用户未做改动
- **WHEN** 协调员读取五个角色的技能域
- **THEN** `DEV` 列出 后端开发 与 前端开发，`QA` 列出 测试，`BA` 列出 业务分析，`PM` 列出 项目管理，`UX` 列出 UI设计
- **AND** 每一项预置技能都恰好出现在一个角色下

#### Scenario: 持有技能不会让人获得第二个角色

- **GIVEN** 人员 `E100` 是 `DEV`，持有 测试 且档位 `Expert`
- **WHEN** 读取其档案，并对一个 `QA` 角色的岗位执行搜索
- **THEN** `E100` 仍然只持有一个角色 `DEV`，且不出现在 `QA` 的合适清单中
- **AND** `E100` 只能通过跨角色栏出现在该岗位面前

#### Scenario: 之后新增的角色其技能域为空

- **GIVEN** 协调员新增角色 `SRE`，且未给它分配任何技能
- **WHEN** 一个 `SRE` 岗位没有 `SRE` 候选人，且兜底被评估
- **THEN** 跨角色栏为空，其他角色的任何技能都不会被当作 `SRE` 的技能域

#### Scenario: 改域不改写已存数据

- **GIVEN** 测试 属于 `QA` 域，且已在其下生成过一份推荐快照
- **WHEN** 协调员把 测试 移到另一个角色的域
- **THEN** 已存的人员、岗位与快照保持原有数据
- **AND** 只有此后进行的搜索才使用新的域

### Requirement: 被引用的目录项冻结，且永不被删除

只要至少一名人员或一个岗位引用了某个角色或技能，系统应拒绝改名、拒绝删除，并提供停用作为替代。在没有任何引用时，名称应可编辑。停用与重新启用不得改写任何已存引用：现有人员、岗位与推荐理由继续展示该项，而新岗位与新导入不得再选择它。维护目录 —— 新增、改名、停用与重新启用 —— 应只提供给协调员。

**Traces:** proposal 步骤 1 与关键规则 "Catalog items are deactivated, never deleted"；REQ-001 §6 目录生命周期；S28。

#### Scenario: 被引用的技能既不能删除也不能改名

- **GIVEN** 后端开发 被 40 名人员与 3 个岗位引用
- **WHEN** 协调员请求删除它
- **THEN** 该操作被拒绝，目录中仍有 后端开发
- **WHEN** 协调员请求改名
- **THEN** 改名被拒绝

#### Scenario: 停用只对新工作隐藏该项

- **GIVEN** 后端开发 已被停用
- **WHEN** 负责人打开新岗位的技能选择器
- **THEN** 选择器中不出现 后端开发
- **AND** 已经要求该技能的岗位仍把它列为 `required`
- **AND** 已经持有该技能的人员仍在档案上显示其档位

#### Scenario: 首次引用之前允许改名

- **GIVEN** 一项无人引用的技能
- **WHEN** 协调员为它改名
- **THEN** 改名成功，目录显示新名称

### Requirement: 人员主数据以工号为键

系统应每个工号保存一名人员，包含姓名、可选邮箱、角色引用、职级档、差旅意愿与 `active` 标记。角色应恰好是一条目录角色，以单一引用持有：一名人员从不持有两个角色，系统中任何路径都不得添加第二个。系统不得提供任何在应用内创建或修改人员主数据的路径；此类变更都应源自导入批次。

**Traces:** proposal 步骤 1–2 与关键规则 "Person master data comes from a report"；REQ-001 §3、§5.1、§9；S13、S17。

#### Scenario: 人员恰好持有一个角色

- **GIVEN** 人员池中已存在一名人员
- **WHEN** 通过界面或数据模型读取任一人员档案
- **THEN** 该人员恰好持有一个角色，且没有任何控件或字段提供第二个
- **AND** 系统中任何操作都不会在不替换现有角色的前提下添加角色

#### Scenario: 档案只读

- **GIVEN** 一名职级为 `Junior` 的人员
- **WHEN** 协调员打开该人员档案
- **THEN** 主数据被展示
- **AND** 没有任何控件提供保存对姓名、邮箱、角色、职级、差旅意愿或启用标记的修改

### Requirement: 三套有序档位刻度

系统应按档位次序比较三套刻度，从不使用自由数字：职级 `Junior` < `Senior` < `Lead` < `Principal`；熟练度 `Novice` < `Advanced beginner` < `Practitioner` < `Proficient` < `Expert`；差旅意愿 `none` < `limited` < `full`。凡展示档位之处，系统应显示档位名称。

**Traces:** proposal 关键规则 "Three ordered band scales"；REQ-001 §5 词表、B18。

#### Scenario: 展示档位名称，从不展示数字

- **GIVEN** 一名人员在 测试 上的熟练度为 `Practitioner`
- **WHEN** 协调员打开候选人搜索结果
- **THEN** 该行显示 `Practitioner`，不显示任何数字等级

#### Scenario: 次序驱动比较

- **GIVEN** 岗位要求 `Senior`，另有两名人员分别为 `Junior` 与 `Lead`
- **WHEN** 评估门槛
- **THEN** `Lead` 人员通过职级门槛，`Junior` 人员被排除

### Requirement: 每人对每项技能至多一个熟练度档

系统对每个“人员—技能”对应至多持有一个档位。导入应插入或覆盖该档位，且不得删除档位。

**Traces:** proposal 步骤 2；REQ-001 §5、§5.1；S11、S15；D6。

#### Scenario: 档位被覆盖，而不是重复

- **GIVEN** 人员 `E100` 在 后端开发 上的档位为 `Novice`
- **WHEN** 一个已应用的批次为 `E100` 上报 后端开发 为 `Practitioner`
- **THEN** 档案中 后端开发 只有一行，档位为 `Practitioner`

#### Scenario: 未出现的技能保留原档位

- **GIVEN** 人员 `E100` 在 测试 上的档位为 `Proficient`
- **WHEN** 一个已应用的批次只列出 `E100` 与 后端开发
- **THEN** 测试 仍为 `Proficient`

### Requirement: 人员档案可供协调员读取

系统应针对一名人员展示：主数据、每项技能及其档位，以及每条占用（当前或已结束），各含所属项目、开始与结束日期，并标出已结束的占用。

**Traces:** REQ-001 §8 展示契约；proposal 步骤 8。

#### Scenario: 档案列出人员的占用

- **GIVEN** `E100` 自 2027-02-01 至 2027-06-30 被派在项目 `Atlas` 上，另有一段更早的 `Borealis` 占用，2026-01-01 至 2026-03-31
- **WHEN** 协调员打开该档案
- **THEN** 档案列出两条占用及其所属项目、开始与结束日期
- **AND** 已结束的 `Borealis` 占用被标为已结束
